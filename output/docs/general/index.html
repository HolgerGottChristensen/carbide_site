Application Structure
\n
The main element of Carbide is an application. This is the main struct allowing you to run Carbide. This application struct holds the state of the program, its environment, and allows processing events, and manages focus.
\n
The outermost environment contains values provided by the outside environment, for example the OS. An example of this is the preferred text size, and accent color (To-Be). The environment is considered immutable, and functions using shadowing. This is described in further detail here.
\n
The main use of the application is to allow managing one or multiple scenes. A scene is an abstraction that holds a set of widgets that for example can be rendered. A classic example of a Scene is a Window. Another example is a WindowGroup, where the group allows spawning and managing multiple of the same window. Scenes are a hierarchy, and a Scene can contain child Scenes. For example this could be a window that requires a sub window, where if the window is closed all the child windows are also closed.
\n
A scene decides how to present its containing widgets, and how to respond to events. A window might render to a desktop window and allow handling mouse and keyboard events. It might decide to render at a constant framerate, whenever the OS requests it, or when receiving events. A pdf, might only care about rendering, and layout.
\n
To run your application, you call .launch() on the application struct. This is a blocking call, and will start the event loop behind the scenes and depending on the target (for example wasm), will handle the implementation details of launching the code.

Colors
\n
When rendering in Carbide, each shape can have a Color. In Carbide, this color is specified using an enum (in color.rs), and can be constructed on multiple different ways.
\n
The most common way to create a new Color is by using its Color::new_rgb() or Color::new_rgba() methods. These will construct a RGBA color based on the different color components given as input.
\n
Carbide has a few predefined colors. These can be used as simple debugging colors. The predefined colors are not recommended to be used, since they were migrated over when we forked Conrod in 2021, and has not been updated since.
\n
A color can also be used in a Gradient, allowing you to create more complex visual effects.
\n
A few other interesting ways of constructing a color exist. You can generate a random color using Color::random() method, which creates a new random color each time the method is called. You can also generate a new color based on the current time using the Color::time() method. This rotates through different hues of an HSL color based on the current time.
\n
\n
It is recommended, when rendering, to use EnvironmentColor, and not use the Color type directly. This enables Carbide to apply themeing and other modifications to the color based on user preferences, such as lightmode, darkmode, and custom themes. It also allows custom overrides higher in the widget tree, for example setting the EnvironmentColor red, to another shade, or an entirely different color.
\n
\n
The color example
\n
The colors example showcases the different EnvironmentColor's when rendered using the current Theme.
\n
\n
Run the example
\n
The example can be run with the following command: cargo run --package carbide_wgpu --example colors when located in the working directory carbide.
\n
For better performance, remember to run the example with --release.
\n
Color reprensentation
\n
In Carbide, colors can be represented in two diffrent ways. Either the color is specified using the RGBA components or the HSLA components.
\n
Carbide converts between the different colors based on the methods you call.
\n
EnvironmentColor
\n
An EnvironmentColor provides a mechanish of using semantic and configurable colors instead of choosing a color with specific RGB values. The most common color variants are the Accent and the Label.
\n
The accent environment color is the default color for the different shapes, such as Rectangle, Circle, Capsule and more.
\n
The label environment color is the default color for rendering Text and icon images.
\n
EnvironmentColor's are configurable in the Environment, and can be overridden by inserting them into the widget tree. The EnvironmentColor is inherited by the widget children, and the closest override to the thing being rendered takes precedence.

Environment
\n
One of the most common structures of Carbide is the Environment. The Environment is a scoped dictionary of keys and values. When Carbide processes events, calculates layouts or does rendering, an Environment is provided to the Widget, containing all the state that can be used while processing. This could include settings, the current theme, and custom state. Values can be added and updated in the Environment, and due to its lifetime and scoping rules, can be provided when processing a widgets children.
\n
The Environment can contain both mutable and immutable references to a given value. Since the Environment contains references to its values, a Widget can provide contained state to its children, while still adhering to rust's strict borrowing rules.
\n
The mechanism is also used by Carbide to provide Manager's, for example allowing a widget within a window, to request the window to be closed, requesting focus, or requesting a new animation frame.
\n
One of the most common examples of where the environment is used in Carbide is EnvironmentColor. The environment contains an Accent color, which can be overridden within a widgets children.
\n

Scoping rules
\n
The environment contains scoped values, and allows for shadowing. Scoping follows the same shadowing rules as Rust. Scoping is on a per key basis. Only one value can be current in the environment per key. If you insert a new value into the environment with a key that is already inserted, the previous value will be shadowed by the new value.
\n
This is for example used when defining styles for carbide controls. Suppose we have a default button style. This could be inserted at the outermost position in the environment. A specific style can be then inserted, overriding the other style, for all widgets contained in the scope of the environment. When leaving the scope, the outermost value can be accessed again.
\n
It is not possible to access the value from the outer environment in the inner environment.

Environment
\n
One of the most common structures of Carbide is the Environment. The Environment is a scoped dictionary of keys and values. When Carbide processes events, calculates layouts or does rendering, an Environment is provided to the Widget, containing all the state that can be used while processing. This could include settings, the current theme, and custom state. Values can be added and updated in the Environment, and due to its lifetime and scoping rules, can be provided when processing a widgets children.
\n
The Environment can contain both mutable and immutable references to a given value. Since the Environment contains references to its values, a Widget can provide contained state to its children, while still adhering to rust's strict borrowing rules.
\n
The mechanism is also used by Carbide to provide Manager's, for example allowing a widget within a window, to request the window to be closed, requesting focus, or requesting a new animation frame.
\n
One of the most common examples of where the environment is used in Carbide is EnvironmentColor. The environment contains an Accent color, which can be overridden within a widgets children.
\n

Scoping rules
\n
The environment contains scoped values, and allows for shadowing. Scoping follows the same shadowing rules as Rust. Scoping is on a per key basis. Only one value can be current in the environment per key. If you insert a new value into the environment with a key that is already inserted, the previous value will be shadowed by the new value.
\n
This is for example used when defining styles for carbide controls. Suppose we have a default button style. This could be inserted at the outermost position in the environment. A specific style can be then inserted, overriding the other style, for all widgets contained in the scope of the environment. When leaving the scope, the outermost value can be accessed again.
\n
It is not possible to access the value from the outer environment in the inner environment.
